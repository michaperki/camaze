Security

Read-only by design.

camaze reads billing and usage data from the providers you connect. It has no code path to create, modify, or delete anything in a connected provider account — and every security-relevant action taken inside camaze itself is logged.

The short version

Read-only provider access. AES-256-GCM encryption of credentials at rest. TLS in transit. Row-level security for tenant isolation. Provider keys are never returned to the browser in full. Every security-relevant account change is recorded in an append-only audit log.

Provider access

camaze only reads.

Each connected key is used exclusively to call that provider's own billing or usage-reporting endpoint — Anthropic's cost report, OpenAI's Costs API, Google's BigQuery billing export. There is no request path anywhere in camaze that writes to a provider account.

Encryption

AES-256-GCM at rest, TLS in transit.

Provider credentials are encrypted with AES-256-GCM before they're stored, using a key that lives only in camaze's server environment — never alongside the ciphertext it protects. Every connection to camaze, and every connection camaze makes onward to Supabase or a provider's API, is TLS-encrypted.

Tenant isolation

Every query scoped to one account, twice over.

Every server-side query is explicitly scoped to the requesting user's account. Postgres row-level security policies enforce the same boundary independently at the database level, so a bug in application-level scoping isn't the only thing standing between one customer's data and another's.

Two independent boundaries
  • Application layer — every query is scoped to the caller's account before it runs.
  • Database layer — row-level security policies enforce the same scoping independently.
Audit logging

Every change, logged — and it stays that way.

Connecting or removing a provider key, changing a budget, editing departments and people, reassigning attribution, changing notification settings, signing in — each is recorded with who, what, and when. The log is append-only: there is no code path to edit or delete an entry, and the database itself rejects any attempt to alter one, including from camaze's own server credentials.

In plain terms

What camaze can and cannot do

Can
Read
  • Read billing and usage data from Anthropic, OpenAI, and Google using the credential you provide.
  • Store that credential, encrypted, so it can keep reading on a schedule.
  • Log the security-relevant actions taken inside camaze itself.
Cannot
No write access
  • Create, modify, or delete anything in a connected provider account.
  • Make API calls, spend money, or consume quota on your behalf with a connected key.
  • Rotate, revoke, or otherwise change a key at the provider — only within camaze.
